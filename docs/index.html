THE APPROACH

Read the code. Trace the behavior. Identify the trade-offs. Measure before making performance claims. Every claim on this site is labelled as verified, analysis, or open hypothesis.

00 / EVIDENCE STATUS

33 tests, executed.

Thirty-three scenarios run against Zed's own crates at a pinned revision: five adversarial insert/delete cases and a six-order permutation case against text, each asserting Zed's own check_invariants(); eight against clock, which ships with no tests of its own; five against scheduler, pinning the priority weights and the !Send executor boundary; and fourteen against sum_tree and rope, covering copy-on-write independence, summary aggregation, seek bias, and byte-versus-character columns.

02 / EVIDENCE MODEL

Engineering, not guesswork.

This project distinguishes what the source code proves from what an engineer can reasonably infer, and from questions that still need experiments. Benchmarks are workload-specific; implementation details are tied to upstream source.

Three levels of confidence.

VERIFIED Directly supported by inspected source code or tests.

ANALYSIS An interpretation of observed implementation and likely consequences.

HYPOTHESIS An open claim requiring more tracing, tests, or measurement.

03 / RESEARCH PRINCIPLES

A / SOURCE FIRSTImplementation before interpretation.Use exact paths, symbols, tests, and revision context.
B / TRACE END TO ENDConnect the layers.Follow an operation from public API to mutation, storage, history, and synchronization.
C / MEASURENo performance theatre.Separate asymptotic reasoning from observed benchmark results.
D / STAY HONESTExpose what's unknown.Keep open questions visible and update conclusions when the code changes.
